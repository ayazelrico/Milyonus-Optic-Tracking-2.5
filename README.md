# Milyonus Optic Tracking v3.0 — 90-Day Hustle Plan

> **One measurable improvement. Every day. No random feature development.**

The purpose of this roadmap is straightforward but ambitious: to transform Milyonus Optic Tracking from a capable technical demonstration into a dependable, interpretable, and product-grade optic intelligence engine.

MediaPipe is the infrastructure layer. The durable value we build on top of it will be our **Proprietary Intelligence Layer**: the measurement models, temporal reasoning, behavioral interpretation, personalization, reliability mechanisms, and developer-facing capabilities that make the system distinctly ours.

## Six-Phase Roadmap

| Phase | Days | Strategic Objective |
|---|---:|---|
| **Phase 1 — Measurement Foundation** | 1–15 | Establish trustworthy measurement and a reproducible baseline: landmark jitter, temporal smoothing, confidence calibration, and unified signal schemas. |
| **Phase 2 — Tracking Intelligence** | 16–30 | Model how a face evolves through time: velocities, accelerations, gaze transitions, track continuity, and focus episodes. |
| **Phase 3 — Behavioral Intelligence** | 31–45 | Progress from “Where is the face?” to “How does the face behave?” through personal deviation analysis, posture patterns, event timelines, and session summaries. |
| **Phase 4 — Personalization** | 46–60 | Replace rigid universal thresholds with adaptive calibration: calibration mode, camera and distance compensation, and signal-quality scoring. |
| **Phase 5 — Performance & Reliability** | 61–75 | Bring the system to production-grade maturity: separate rendering from inference, introduce worker architecture, test for memory leaks, and implement robust error recovery. |
| **Phase 6 — Product Intelligence** | 76–90 | Convert the technical foundation into a product surface: dashboards, heatmaps, automated insights, a developer API, an SDK, and the v3.0 readiness review. |

## Daily Operating Cycle — The Hustle Rule

Every working day follows the same disciplined nine-step operating cycle:

1. **Observe:** Identify a missing, noisy, unstable, or misleading metric.
2. **Diagnose:** Determine the current failure mode and establish a measurable baseline.
3. **Hypothesize:** State precisely what should improve, and by which metric, if the proposed change is effective.
4. **Implement:** Deliver one narrowly scoped change; the target effort is 30 minutes to 3 hours.
5. **Test:** Validate the change with a real camera whenever possible, alongside the relevant automated tests.
6. **Measure:** Compare the new result against the previous implementation using reproducible measurements.
7. **Review:** Check for regressions in accuracy, stability, latency, resource usage, interpretability, and backward compatibility.
8. **Commit:** Treat one logical change as one commit, using `feat`, `fix`, `perf`, or `refactor` as appropriate.
9. **Record:** Complete the daily record with the objective, change, metric, result, regression status, and next action.

> **Golden Rule:** If we cannot answer the question *“Which measurement does this feature improve?”*, we do not write that feature today.

# Milyonus Optic Tracking v3.0 — 90 Günlük Hustle Planı

Bunun üzerine inşa edeceğimiz kalıcı değer, **Proprietary Intelligence Layer** olacaktır: sistemi özgünleştiren ölçüm modelleri, zamansal akıl yürütme, davranışsal yorumlama, kişiselleştirme, güvenilirlik mekanizmaları ve geliştirici odaklı yetenekler.

## Günlük Çalışma Döngüsü — Hustle Rule

Her çalışma günü aynı disiplinli dokuz adımlık operasyon döngüsüyle ilerler:

1. **Observe:** Eksik, gürültülü, kararsız veya yanıltıcı metriği tespit et.
2. **Diagnose:** Mevcut hata modunu belirle ve ölçülebilir bir baseline oluştur.
3. **Hypothesis:** Önerilen değişikliğin hangi metriği, ne yönde iyileştirmesi gerektiğini açıkça tanımla.
4. **Implement:** Kapsamı dar, tek bir değişiklik uygula; hedef süre 30 dakika ile 3 saat arasındadır.
5. **Test:** Mümkün olduğunda gerçek kamera ile ve ilgili otomatik testlerle doğrulama yap.
6. **Measure:** Yeni sonucu, tekrarlanabilir ölçümler kullanarak önceki uygulamayla karşılaştır.
7. **Review:** Accuracy, stability, latency, kaynak kullanımı, yorumlanabilirlik ve geriye dönük uyumluluk açısından regression kontrolü yap.
8. **Commit:** Tek mantıksal değişikliği tek commit olarak kaydet; uygun yerde `feat`, `fix`, `perf` veya `refactor` kullan.
9. **Record:** Objective, change, metric, result, regression durumu ve next action alanlarını içeren günlük kaydı tamamla.

> **Altın Kural:** *“Bu özellik hangi ölçümü geliştiriyor?”* sorusuna cevap veremiyorsak, o gün o özelliğin kodunu yazmayız.
